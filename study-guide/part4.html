12. Services, dependency injection, hooks, events, plugins

12.1 Services and the container

Service = a PHP object with one job (logger, mailer, database, current user, entity type manager). The service container creates them lazily and shares one instance. Services are declared in MODULE.services.yml.

# training.services.yml
services:
  training.greeter:
    class: Drupal\training\Greeter
    arguments: ['@current_user', '@logger.factory', '@entity_type.manager']
namespace Drupal\training;

use Drupal\Core\Session\AccountProxyInterface;
use Drupal\Core\Logger\LoggerChannelFactoryInterface;

class Greeter {
  public function __construct(
    protected AccountProxyInterface $currentUser,
    protected LoggerChannelFactoryInterface $loggerFactory,
  ) {}

  public function greet(): string {
    $this->loggerFactory->get('training')->info('Greeted @u', ['@u' => $this->currentUser->getDisplayName()]);
    return 'Hello ' . $this->currentUser->getDisplayName();
  }
}

Autowiring is available (autowire: true) in Drupal 10.2+. You can also use \Drupal::service('training.greeter') in procedural code, but inside classes use injection.

12.2 Dependency injection in controllers, forms, blocks

Classes that are created by Drupal (controller, plugin, form) use ContainerInjectionInterface or ContainerFactoryPluginInterface with a static create() factory:

use Symfony\Component\DependencyInjection\ContainerInterface;
class HelloController extends ControllerBase {
  public function __construct(protected Greeter $greeter) {}
  public static function create(ContainerInterface $container): static {
    return new static($container->get('training.greeter'));
  }
  public function greet(): array { return ['#markup' => $this->greeter->greet()]; }
}

Why DI? Testability (swap dependencies with mocks), loose coupling, and no hidden globals. ControllerBase already gives helpers like $this->currentUser(), $this->entityTypeManager(), $this->config().

12.3 Hooks

Meaning: A hook is a named extension point. Modules implement it to alter or add behavior.

Drupal 11 object-oriented hooks (use this style in new code)

namespace Drupal\training\Hook;

use Drupal\Core\Hook\Attribute\Hook;
use Drupal\Core\Entity\EntityInterface;

class TrainingHooks {
  #[Hook('node_presave')]
  public function nodePresave(EntityInterface $entity): void {
    if ($entity->bundle() === 'event' && $entity->isNew()) {
      $entity->setTitle(trim($entity->getTitle()));
    }
  }

  #[Hook('form_alter')]
  public function formAlter(array &$form, \Drupal\Core\Form\FormStateInterface $form_state, string $form_id): void {
    if ($form_id === 'node_event_form') {
      $form['title']['widget'][0]['value']['#description'] = t('Keep it short.');
    }
  }
}

Classic procedural style still works: in training.module write function training_node_presave($node) {...}. After adding hooks run drush cr. Hooks classes sit in src/Hook/.

12.4 Events (Symfony event subscribers)

Meaning: Use events (from Symfony) for request/response lifecycle and for newer subsystems. Hooks vs events: hooks are Drupal-specific and discovered by name; events use a dispatcher and subscribers with priorities.

# training.services.yml
  training.redirect_subscriber:
    class: Drupal\training\EventSubscriber\RedirectSubscriber
    tags:
      - { name: event_subscriber }
namespace Drupal\training\EventSubscriber;
use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Component\HttpKernel\Event\RequestEvent;
use Symfony\Component\HttpKernel\KernelEvents;

class RedirectSubscriber implements EventSubscriberInterface {
  public static function getSubscribedEvents(): array {
    return [KernelEvents::REQUEST => ['onRequest', 30]];   // priority 30
  }
  public function onRequest(RequestEvent $event): void {
    // e.g. redirect /old to /new
  }
}

Typical events: KernelEvents::REQUEST / RESPONSE / EXCEPTION, RoutingEvents::ALTER, ConfigEvents::SAVE.

13. Entity API, database API, config API, state, cache, queue, cron

13.1 Entity API

Entity types: content entities (node, user, taxonomy_term, media, file, comment, block_content, paragraph) are fieldable and stored in tables; config entities (view, node_type, field_config, role, image_style) are stored in config.

use Drupal\node\Entity\Node;

// create
$node = Node::create([
  'type' => 'event',
  'title' => 'Drupal Meetup',
  'field_location' => 'Hyderabad',
  'status' => 1,
]);
$node->save();

// load
$node = Node::load(5);
$nodes = \Drupal::entityTypeManager()->getStorage('node')->loadMultiple([1, 2]);

// read/write fields
$title = $node->label();
$loc = $node->get('field_location')->value;
$node->set('field_location', 'Pune')->save();
$term = $node->get('field_category')->entity;         // referenced entity
$ids = array_column($node->get('field_category')->getValue(), 'target_id');

// delete
$node->delete();

// entity query
$ids = \Drupal::entityQuery('node')
  ->accessCheck(TRUE)
  ->condition('type', 'event')
  ->condition('field_featured', 1)
  ->sort('created', 'DESC')
  ->range(0, 10)
  ->execute();
Always call accessCheck(TRUE|FALSE) on entity queries (required since Drupal 10). Use TRUE for user-facing output.

Entity concepts for interviews

  • Entity type (definition class with handlers: storage, view builder, access, list builder, forms, route provider); bundle; fields: base fields (code-defined, e.g. title) vs configurable fields (UI-defined).
  • Revisions and translations are built into content entities.
  • Custom entity: define with the #[ContentEntityType] attribute, an interface, schema via base field definitions, and handlers. Scaffold with drush generate entity:content. Update schema changes with hook_update_N and EntityDefinitionUpdateManager.
  • Entity access: $entity->access('update', $account).
  • Typed data / field items: $node->field_x is a FieldItemList of FieldItems.

13.2 Database API

$database = \Drupal::database();

// select
$result = $database->select('node_field_data', 'n')
  ->fields('n', ['nid', 'title'])
  ->condition('n.type', 'event')
  ->condition('n.status', 1)
  ->orderBy('n.created', 'DESC')
  ->range(0, 5)
  ->execute();
foreach ($result as $row) { echo $row->title; }

// insert / update / delete
$database->insert('training_log')->fields(['msg' => 'Hi'])->execute();
$database->update('training_log')->fields(['msg' => 'Bye'])->condition('id', 1)->execute();
$database->delete('training_log')->condition('id', 1)->execute();

// transaction
$tx = $database->startTransaction();   // rolls back when $tx goes out of scope on exception
Never concatenate user input into SQL. Use placeholders (:name) or the query builder; this prevents SQL injection.

Entity query vs DB query: use entity query for entity IDs with access/field abstraction; use the DB API for custom tables or performance-critical aggregates.

13.3 Configuration API

$config = \Drupal::config('system.site');           // read only
$name = $config->get('name');
$editable = \Drupal::configFactory()->getEditable('training.settings');
$editable->set('greeting', 'Hi')->save();

Simple config (a single object like system.site) vs config entities (many, like views). Schema in config/schema is required, or you get "missing schema" errors in tests.

13.4 State API, key/value, settings

  • State: \Drupal::state()->set('training.last_run', time()); — environment-specific values not exported (last cron time).
  • Key-value store: general storage keyvalue / keyvalue.expirable.
  • Settings (settings.php): \Drupal\Core\Site\Settings::get('hash_salt') — credentials and server-specific values.
  • Rule: editors change it → config; code/environment sets it → settings; runtime-only memory → state; user-generated data → entity.

14. Security

14.1 Threats and Drupal's defences

ThreatMeaningPrevention in Drupal
XSS (cross-site scripting)Attacker injects JavaScript into pagesTwig auto-escapes; use #markup (filtered) or #plain_text; Xss::filterAdmin(), Html::escape(); never |raw on user input; restrict text formats.
SQL injectionAttacker alters SQLUse query builder / placeholders. No string concatenation.
CSRFForged requests by a logged-in userForm tokens automatic; routes with _csrf_token: 'TRUE' requirement for links that change data.

File upload attacksMalicious filesRestrict extensions, use private files for sensitive data, never allow php/exe.
Brute forcePassword guessingFlood control (core), Login Security, strong passwords, 2FA module.

14.2 Security checklist

  • Use HTTPS; set $settings['trusted_host_patterns'] in settings.php.
  • Keep core and contrib updated: composer audit, Available updates report.
  • Least-privilege roles; do not hand out "administer ..." permissions.
  • Use "Basic HTML" for authenticated users, "Restricted HTML" for anonymous; Full HTML for admins only.
  • Protect settings.php: chmod 444; put sites/default/files/private outside the web root: $settings['file_private_path'] = '../private';.
  • Disable dev modules (devel, webprofiler) in production.
  • Change user 1's name from "admin"; use strong passwords; consider 2FA.
  • Block users from PHP execution in files directories (Apache/Nginx rules; Drupal writes .htaccess).
  • Check /admin/reports/status for warnings, and use the Security Review module.
  • Do not run update.php access publicly ($settings['update_free_access'] = FALSE;).

14.3 Code-level security patterns

use Drupal\Component\Utility\Html;
use Drupal\Component\Utility\Xss;

$filtered = Xss::filter($user_input);                // allows safe tags

Exercise 14.1

Task: A teammate wrote '#markup' => '<p>Hello ' . $_GET['name'] . '</p>'. Explain the vulnerability and fix it.
Answer: It is reflected XSS: ?name=<script>...</script> runs script in the visitor's browser. Fix: use the Request object, a placeholder and escaping: 
$name = \Drupal::request()->query->get('name', '');
return ['#markup' => $this->t('Hello @name', ['@name' => $name])];

15. Performance and caching

15.1 Drupal cache layers

LayerMeaning
Internal Page CacheCaches full pages for anonymous users (core module).
Dynamic Page CacheCaches pages for all users except the personalised parts (placeholders).
BigPipeStreams cacheable page parts first, then personalised parts.

Twig cacheCompiled templates in PHP files.
Views cacheQuery results and rendered output (Tag based / Time based).
Cache binsStorage buckets: default, render, data, discovery, bootstrap, config, entity, menu, page, dynamic_page_cache.
BackendDatabase by default; Redis/Memcache for speed.

15.2 Cache metadata (the 3 pieces) — very common question

MetadataMeaningExample
Tags"What data did this depend on?" When tagged data changes, the cache is invalidated.node:5, node_list, config:system.site, user:3
Contexts"What request conditions cause variations?" One cached copy per context value.user.roles, languages, url.path, url.query_args, route, theme, user.permissions
Max-age"How long can this be cached?" 0 = never cache (avoid; it disables page cache), Cache::PERMANENT = until tags invalidate.3600
$build['#cache'] = [
  'tags' => ['node_list:event', 'config:training.settings'],
  'contexts' => ['user.roles', 'url.query_args:category'],
  'max-age' => Cache::PERMANENT,
];
// a node: $node->getCacheTags() returns ['node:5']
Interview one-liner: "Drupal's cache is correct by default: every render array carries tags, contexts and max-age. Cache invalidation is by tag, so editing a node automatically refreshes every page that displayed it."

Lazy builders / placeholders

For personalised or uncacheable parts (cart count, username) use #lazy_builder so the rest of the page stays cached and BigPipe/dynamic page cache fills in the placeholder.

15.3 Performance settings and tuning

  • Configuration → Development → Performance (/admin/config/development/performance): browser and proxy cache max age, aggregate CSS/JS (on in production), clear all caches.
  • Enable Internal Page Cache, Dynamic Page Cache, BigPipe.
  • Use Redis for cache and locks; Varnish or a CDN (Cloudflare, Fastly) for full-page caching with tag-based purging.
  • Optimise images: image styles, WebP, lazy loading, responsive images.
  • Views: avoid loading all entities for huge lists; use fields instead of full entity rendering; add pagers; use caching; avoid heavy relationships.
  • Database: indexes on custom tables, avoid N+1 queries (use loadMultiple), PHP OPcache enabled, current PHP version.
  • Profiling tools: Devel/Webprofiler (dev), Blackfire, New Relic, Xdebug profiler, ddev xdebug.

Exercise 15.1

Task: A block shows "Latest 3 events" but new events do not appear for an hour. Why, and what is the right fix?
Answer: The block uses max-age 3600 without a tag for the list. 17. Migrate, JSON:API, headless, multilingual, deployment

17.1 Migrate API

Meaning: A framework to import data from other sources (CSV, JSON, SQL, another Drupal site) into Drupal. Pipeline: source → process (transform field by field) → destination. IDs are tracked in map tables to support rollback and updates.

# or core-only: migrations/events_csv.yml

  plugin: csv           # from migrate_source_csv
  path: modules/custom/training/data/events.csv
  ids: [id]
process:
  title: name
  field_location: place
  type:
    plugin: default_value
    default_value: event

  plugin: entity:node
ddev composer require drupal/migrate_plus drupal/migrate_tools drupal/migrate_source_csv

ddev drush migrate:status
ddev drush migrate:import events_csv

Core Drupal-to-Drupal upgrades (7 → 10/11) use the migrate_drupal and migrate_drupal_ui modules (/upgrade). Common process plugins: get, default_value, static_map, migration_lookup, concat, explode, callback, format_date, skip_on_empty, sub_process, entity_generate.

17.2 JSON:API and REST (headless Drupal)

  • JSON:API (core) automatically exposes all entities: /jsonapi/node/event, /jsonapi/node/event/{uuid}. Supports filter, sort, page[limit], include, fields[node--event]=title,field_location.
  • Enable: ddev drush en jsonapi -y. Config: /admin/config/services/jsonapi (read-only mode recommended unless you need writes).
  • Example: /jsonapi/node/event?filter[field_featured]=1&sort=-created&page[limit]=5&include=field_category
  • RESTful Web Services (core): custom resources and Views "REST export" display.
  • GraphQL (contrib) is an alternative.
  • Authentication: cookie (same domain), Basic Auth (core), OAuth2 / Simple OAuth (contrib), JWT (contrib). Always use HTTPS.
  • CORS: in sites/default/services.yml: cors.config: enabled: true, allowedOrigins: ['https://app.example.com'].
  • Decoupled / headless: Drupal as the back end, a JS front end (Next.js, Nuxt, React). Progressively decoupled: Drupal renders pages and parts use JS components.

17.3 Multilingual

  1. Enable language, content_translation, locale (interface translation), config_translation.
  2. Add languages: Configuration → Regional and language → Languages → Add language.
  3. Detection: Languages → Detection and selection (URL prefix /fr/..., domain, session, browser, user).
  4. Enable translation for content type: Configuration → Regional and language → Content language and translation (/admin/config/regional/content-language) → tick Content → Event → mark fields translatable.
  5. Translate: Node → Translate tab → Add. Interface strings: Configuration → Regional and language → User interface translation. Config: Configuration → Regional and language → Configuration translation.

Commands: drush locale:check, drush locale:update. Use $this->t() and {{ 'text'|t }} for all strings.

17.4 Deployment workflow

# local
git pull
ddev composer install
ddev drush updb -y
ddev drush cim -y
ddev drush cr

# production deploy script (typical)
git pull origin main
composer install --no-dev --optimize-autoloader
drush maintenance:set 1   # optional (drush state:set system.maintenance_mode 1)
drush updb -y
drush cim -y
drush cr
drush maintenance:set 0
  • Order matters: code → composer install → updb → cim → cr.
  • Environments: local (DDEV) → dev → staging → production. Content flows production → down (database copy); config flows up (via Git).
  • Hosting: Acquia, Pantheon, Platform.sh / Upsun, DDEV Pro, Amazon, plain VPS with Nginx + PHP-FPM + MariaDB.
  • CI/CD: GitHub Actions / GitLab CI / Jenkins: install, lint (phpcs), static analysis (phpstan), tests (phpunit), then deploy.
  • Version control: commit composer.json, composer.lock, config/, web/modules/custom, web/themes/custom. Do not commit vendor/ (unless host requires), web/core and contrib (installed by composer), web/sites/default/files, settings.local.php.
  • Backups: drush sql:dump --gzip --result-file=../backup.sql and file backups.
  • Maintenance mode: /admin/config/development/maintenance.

17.5 Multisite, install profiles, distributions

  • Multisite: one codebase, multiple sites in web/sites/<name>/, with sites.php mapping domains. Pros: shared code updates; cons: shared failure points.
  • Install profile: predefines modules/config at install (Standard, Minimal, Demo Umami).
  • Distribution: profile + code for a use case (Drupal CMS, OpenSocial).

ddev drush en jsonapi -y
curl "https://drupal112-training.ddev.site/jsonapi/node/event?filter[field_featured]=1&include=field_category&fields[node--event]=title,field_location,field_category&fields[taxonomy_term--event_category]=name"
Anonymous users need "Access content" permission. Terms are returned in the included array.
